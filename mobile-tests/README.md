# FitFuel Mobile — Android Appium Test Suite

This is the mobile-testing counterpart to `backend-tests/` and
`selenium-tests/` in this repo. It tests `fitfuel_mobile/`, the Flutter
Android app, using Appium's `flutter-driver` automation, following the
same battle-tested methodology your friend used on their own project —
adapted here to what this repo actually contains, not copied blind.

**402 test cases**, organized into 20 modules, covering every screen the
app currently has a working navigation path to.

---

## Before you do anything else: read this

This suite was built in a sandboxed environment with **no Android SDK,
no emulator, no GPU/KVM, and no network access to download either**. It
has never been run against a real device. Everything in here — the
framework, the page objects, the 402 test cases, the CI workflow — is
real, complete, and ready to run, but **you need to run it yourself**
once on a machine (or CI runner) that has an actual Android
emulator/device before you can trust any pass/fail number.

The `reports/` folder included in this bundle was generated by
`simulate_demo_run.py` — a script that takes the **real** 402 collected
test IDs from this suite and assigns them a plausible pass/fail/skip
outcome, purely so you can see the exact report format (Excel sheets,
HTML dashboard, JSON) before running anything for real. **Every number
in that sample report is fabricated.** Do not put it in front of an
evaluator as if it were a real run. Delete `reports/` and run the real
thing (see "Running it" below) before you need real numbers.

`simulate_demo_run.py` itself is not part of the test suite — it's a
one-time illustration tool. Delete it once you've run the real suite
once.

## How the app was made testable

Appium's Flutter automation needs two things the app didn't have before:

1. **A test entrypoint.** `lib/main_test.dart` calls
   `enableFlutterDriverExtension()` before running the real app. It changes
   nothing about production behaviour — it's only built when you explicitly
   target it with `-t lib/main_test.dart`, and it's never shipped.

2. **`ValueKey`s on interactive widgets.** `appium-flutter-driver` can find
   elements by key, by visible text, or by widget type — nothing else (no
   CSS selectors, no XPath, no accessibility-id in the usual sense). Text
   finders break the moment two buttons share a label; type finders break
   the moment a screen has two of the same widget type. Keys are the only
   reliable way to address most of the app's interactive elements, so **84
   `ValueKey`s were added across all 16 screens** plus the shared bottom-nav
   widget, following a consistent `screen_element_purpose` naming
   convention (e.g. `login_email_field`, `progress_log_submit_button`,
   `nav_tab_progress`).

   Run `python3 scripts/key_audit.py` any time after a UI change — it's a
   heuristic source scanner (not a Dart AST parser) that reports which
   interactive widgets still lack a key. Current state: **68/75 (90.7%)**
   of scanned constructors are keyed. The remaining 7 are all understood
   and listed below, not silently missing:

   | File | Widget | Why it's unkeyed |
   |---|---|---|
   | `health_assessment_prefs_screen.dart` (×3) | TextField/TextButton/ElevatedButton | Inside the transient "Add other allergy" `AlertDialog` — low priority, not part of any critical flow |
   | `meal_detail_screen.dart` (×2) | ElevatedButton/OutlinedButton | On the `/meal-detail` screen, which nothing in the app currently navigates to (see below) |
   | `app_widgets.dart` L504 | `SelectableOptionCard`'s internal `GestureDetector` | **Dead code** — `SelectableOptionCard` is defined but never instantiated anywhere in the current codebase |
   | `app_widgets.dart` L572 | `SelectableChip`'s internal `GestureDetector` | False positive — the *outer* `SelectableChip(key: ...)` call sites (health-prefs allergy chips) already attach a key to this exact widget; the audit script can't see through the class boundary |

   Three unkeyed widgets that *were* found and *fixed* while building this
   suite (not in the original app): the password-visibility toggle inside
   the shared `_PasswordField` widget on the Profile screen, the shared
   `FitFuelAppBar` back button (which also had no `tooltip`, so it had no
   accessible label either — added one), and Progress's empty-state "Log
   First Entry" button.

No screen's layout, copy, or behavior was changed. Every edit is either a
`key:` parameter, a `main_test.dart` file, or a `pubspec.yaml`
dev-dependency addition.

## Findings from building this suite

Building 400+ real tests against the real app surfaced a few things
worth flagging to whoever owns this codebase next — recorded here rather
than silently worked around, per the "test what's actually there"
approach this whole suite follows:

1. **`/meal-detail` is unreachable from the UI.** The screen is fully
   built and registered as a named route, but `RecommendationsScreen`'s
   order buttons call `_placeOrder()` with an external Swiggy/Zomato deep
   link instead of pushing this route, and nothing else links to it
   either. `tests/test_07_meal_plan.py::TestMealDetailStub` documents
   this as an `xfail` (expected-to-fail) test rather than skipping it
   silently, so it surfaces in every report until someone wires a tap
   target to it.

2. **Password-length minimum is inconsistent.** `backend/src/routes/auth.routes.ts`
   sets `password: z.string().min(6)` for registration but
   `newPassword: z.string().min(8)` for changing your password — two
   different rules for what a user would reasonably expect to be the same
   constraint. Locked in by
   `tests/test_11_input_validation.py::test_change_password_seven_char_boundary_mismatch`.

3. **`mobile-ci.yml`'s path filter looks stale.** The existing
   `.github/workflows/mobile-ci.yml` filters on `paths: mobile/**`, but the
   Flutter app actually lives at `fitfuel_mobile/`. As written, that
   workflow likely never triggers on mobile app changes. Not fixed here
   (out of this suite's scope) — flagging it since it's a one-line fix.

4. **No dark mode.** `main.dart`'s `MaterialApp` sets no `darkTheme` /
   `themeMode`. `test_15_responsiveness.py` documents this rather than
   testing a feature that doesn't exist.

5. **No seeded test accounts**, unlike the reference project this
   methodology came from. Every account-dependent test registers its own
   throwaway account via `unique_email_factory` — see `conftest.py`.

## Running it

### 1. Install dependencies
```bash
cd mobile-tests
pip install -r requirements.txt
```

### 2. Start a real backend the emulator can reach
The Android emulator reaches your machine's `localhost` via the special
`10.0.2.2` alias. Either:

- **Local ephemeral backend** (what CI does — see `android-e2e.yml`):
  ```bash
  cd backend
  npm ci
  DATABASE_URL=postgresql://... npx prisma migrate deploy
  DATABASE_URL=postgresql://... npm run seed
  DATABASE_URL=postgresql://... PORT=4000 npm run start
  ```
- **Deployed backend** — just set `BACKEND_BASE_URL` to it and skip the
  `--dart-define` below (`api_config.dart` already points there by default).

### 3. Build the flutter-driver-enabled debug APK
```bash
cd fitfuel_mobile
flutter pub get
flutter build apk --debug -t lib/main_test.dart \
  --dart-define=API_BASE_URL=http://10.0.2.2:4000
```

### 4. Start an emulator + Appium server
```bash
emulator -avd <your_avd_name> &
appium &
```

### 5. Run the suite
```bash
cd mobile-tests
python3 -m pytest                        # full 402-test run
python3 -m pytest -m smoke               # fast high-value subset
python3 -m pytest -m "not slow"          # skip the expensive network/rotation tests
python3 -m pytest tests/test_08_progress_crud.py   # one module
```

### 6. Generate the reports
```bash
python3 generate_reports.py
```
This reads `reports/execution-results.json` (written automatically by
`conftest.py` when pytest finishes) and produces
`Automation_Test_Report.xlsx`, `execution-report.html`, `dashboard.html`,
and `summary.md` — same format as `selenium-tests/`'s reports, so both
suites read the same way. Exits non-zero if the pass rate is below
`GATE_THRESHOLD_PCT` (default 90%, same knob in both `config.py` and
`android-e2e.yml` — see the "90-vs-95 drift" note below).

## Timeout tuning

`Appium-Python-Client==3.1.1` + `selenium==4.21.0` don't reliably respect
`socket.setdefaulttimeout()` for Appium HTTP calls, and the "obvious" fix
(`AppiumClientConfig`) doesn't exist at this client version — importing it
raises `ImportError` and kills the entire collection with zero tests
found. The actual mechanism at this version is
`AppiumConnection.set_timeout(seconds)`, called once at import time
before any session exists. See `utils/appium_connection.py` for the
two-tier implementation (short timeout for everyday commands, longer
timeout just for session creation, since installing the APK + completing
the Dart Observatory handshake legitimately takes longer than a single
`find`/`tap`).

## The 90-vs-95 drift (and how this suite avoids repeating it)

`GATE_THRESHOLD_PCT` is defined in exactly one place conceptually —
`config.py` (default `90`, overridable via env var) — and
`android-e2e.yml` sets the same env var rather than hardcoding a second
number in the CI job summary step. Keep it that way: if you ever need a
different threshold, change the env var, not a number buried in a
workflow YAML that quietly drifts from what the Python code actually
enforces.

## Two things `flutter-driver` genuinely can't do

- **`driver.page_source`** returns HTTP 405, permanently. There is no DOM
  to inspect. `page_objects/base_page.py`'s `ROUTE_TEXT_MARKERS` map (one
  distinctive visible string per screen) is the practical workaround —
  it's a heuristic, not a guarantee, and its one known false-positive
  collision (Dashboard's "Meal Plan" quick-card label vs. the Weekly Meal
  Plan screen's own title) is documented right in that file rather than
  hidden.
- **`background_app()`, `set_network_connection()`, and scroll gestures**
  all return HTTP 500 "not supported" on this driver. `utils/adb_helpers.py`
  reimplements all three directly via `adb shell`.

## Version pinning

`requirements.txt` pins exact versions rather than ranges. This
combination of `appium-flutter-finder` + `Appium-Python-Client` +
`selenium` has tight cross-compatibility requirements — several
"newer is better" combinations either fail to import or silently break
the timeout wrapper above. Don't bump these without re-verifying the
whole chain end to end.
